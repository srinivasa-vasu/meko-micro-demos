Use case 1 · SDLC · Retail checkout

Rehearse before you release: a routine schema change on the busiest table.

The store-pickup feature needs four new things on orders, the table checkout writes on every purchase. The pull request looks routine; a reviewer would approve it. Release management's agent must decide before the change board meets.

The change

Customers can now buy online and pick up in store. To support it, each order needs:

How it is fulfilled
Shipped or picked up, with only those two values allowed.
A public order reference
A unique id for the pickup code, generated for every order.
Which store
Linked to the stores table.
A fast lookup for each store's pickups
A new index.

A second release makes the reference required and unique, and removes an older index the author believes the new one replaces. Both run while checkout takes orders and the nightly reporting job reads the table.

What can go wrong

  • The whole table is rewritten. Generating a new id for every existing order copies all of them, and no one can write to the table meanwhile.
  • The change waits in line, and checkout waits behind it. The nightly report holds the table for up to 40 minutes; this happened before (INC-2291: checkout stalled 11 minutes).
  • Checks that freeze writes. Validating every row, and building the new index, block new orders until they finish.
  • A dashboard slows to a crawl. The "replaced" index is the one the warehouse's pick list relies on.
  • The undo was never tried. And it is needed exactly when things go wrong.

What it costs

  • Checkout stalls: every second is orders not taken.
  • Stores can't pick: the pick-list dashboard times out, pickups run late.
  • Release night becomes an incident, and the next release gets a freeze.
  • The change board approves blind: a PR description, not evidence.
The question: is it safe, and if not, what exactly must change?
Use case 2 · OPS · Operational anomaly

Undo a bad batch job: a defect corrupts orders while checkout keeps writing.

A nightly job, nightly-reprice, ships with a bug in its filter. It runs at night, commits, and is gone before anyone notices. Checkout never stops. The on-call SRE agent opens INC-3107 when the warehouse has nothing to pick.

What happened

A nightly job reprices open orders. Tonight's version has a bug in its filter:

It touches the wrong orders
Every order that was already paid is set back to pending, in one commit, in seconds.
Nothing stops
Checkout keeps taking new orders, some paid and some pending.
The damage hides in plain sight
The wrongly pending orders now sit beside orders that really are pending and orders created since. They look identical.

What can go wrong in the fix

  • Restore last night's backup. Every order taken since the job is lost.
  • Flip "pending" back to "paid". Orders that were never paid become paid, and ship for free.
  • Find the exact moment before the job. The alert says when it was noticed, not when the job ran; the database needs a precise point, and only the job scheduler recorded it.
  • Fix it live. An untested repair on the table checkout is writing to, with no way back.

What it costs

  • Fulfilment stops: no paid orders, nothing to pick or ship.
  • Customers see "pending" for orders they paid for: support calls, double payments.
  • Finance can't reconcile until every row is right again.
  • Hours of forensics, and a repair nobody can prove.
The question: which rows did the job change, exactly, and how do we put back only those?

The world view

Today, a realistic place to try a change is a ticket away, and what teams know does not travel.

How it works today

  • Changes are tried on staging. A copy with a fraction of the rows, none of the traffic, and none of the night jobs. The migration that rewrites 1,000,000 rows takes a second there.
  • Standards live on a wiki. The reviewer has to remember that uuidv7() as a default rewrites the table. Most do not.
  • Incidents end in a postmortem. The SRE team learns that migrations queue behind the 01:00 reporting job. The release team never reads it.
  • Nobody owns "which queries matter". The warehouse's dashboard query is known to the warehouse team, and dropped by a checkout pull request.
  • Undoing a bad job means a restore. Restore the table, or the whole cluster, to before the job, and lose every order written since.
  • Evidence is a PR description. The change board approves on trust, and the incident review reconstructs what happened from chat.

With Meko + AMP

  • Every change is tried on its own branch first. The agent creates it itself, no ticket: a zero-copy fork of main in seconds, with all the data, under checkout's writes and the long transactions an incident names; deleted after.
  • The standard is read by the agent. Rules in the datapack's knowledge base: every limit the rehearsal uses (lock timeout, retries, stall limit, regression factor) comes from the rule that states it.
  • Incidents protect the next release. The SRE team's incident, in a datapack it shares, makes the release agent rehearse with the reporting job running.
  • Critical queries are registered. Teams write them to shared memory; every rehearsal and every repair runs them before and after.
  • Undoing a bad job is surgical. Branch main as of the WAL position the scheduler recorded before the job, compare, repair only the rows it changed. Nothing written since is lost.
  • Every decision has a record. Each step, its numbers and the evidence artifact, on a record read back from the PR or incident id alone.

Use case 2 · OPS

Undo a bad batch job.

A code defect ships in nightly-reprice: it marks every paid order pending. Checkout keeps taking orders, the warehouse has nothing to pick, and the on-call SRE agent opens INC-3107.

Today

  • Restore a backup, or point-in-time-restore the cluster. Every order written since the job is lost, or replayed by hand.
  • Or guess with an UPDATE. "Set pending back to paid": and the orders that were genuinely pending are now paid.
  • The time is known, the position is not. The alert says 02:13; which transaction was the job's lives in the scheduler's logs.
  • The fix is run directly on the live table. Hoping it touches only what it should.

With Meko + AMP

  • Branch main as of just before the job. AMP forks at a past WAL position in seconds, with no running compute on main.
  • Compare, and find exactly the damage. Rows that differ, still hold the job's value, and existed before it. The count must equal what the job's run reported changing.
  • The position comes from Meko. The scheduler's agent recorded it in the shared datapack; the recovery agent finds it from the incident's time.
  • Rehearse the repair on a branch first. Each registered critical query must give back its answer from before the job; then the same repair runs on main.
Use case 2 · How the agents meet

A fork of the past, found through a share.

The scheduler's agent

Knows where: before every job it records the WAL position, with the job and the time, in the same shared datapack.

The recovery agent

Knows neither, and talks to neither. With the share, it finds both: the incident, and the marker from just before the job.

Meko · the right context

The agent knows what applies, and from whom.

  • Each team keeps its own datapack; a share carries it across, no integration to build.
  • Only what applies: incidents about other tables or other topics are set aside, and shown as such.
  • Limits come from the rule that states them: a changed standard changes the next run.
  • Context decides the plan: no reason in the datapack, no extra step.
