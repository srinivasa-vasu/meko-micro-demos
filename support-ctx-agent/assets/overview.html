The use case

A production incident, at two in the morning

An agent can diagnose this. The question is what it costs on the fortieth incident, not the first.

SEV2 · checkout · 02:14

Checkout is failing. The payment provider is timing out. Something shipped forty minutes ago. Twenty services are logging, three dashboards disagree, and the engineer who fixed this exact regression seven months ago has left the company.

Point an agent at it and you get an answer. It reads the telemetry, forms a hypothesis, proposes a fix. That part is now routine — it is the part a good model does well.

Run it a hundred more times and the economics decide whether you keep it. A stateless agent reads everything, every time. It is no cheaper and no faster on the fortieth incident than the first, because it has no way to know it has seen this before. Your costs scale linearly with volume, forever, with no learning curve. That is not a model problem. It is a context problem.

Memory lifecycle
Deciding when a new fact updates an old one rather than joining it. Get this wrong and memory gets stuck on whatever it learned first.
Update and delete as first-class operations, so a record can be corrected or confirmed rather than only appended to. memory_update · memory_delete_by_id
Organisational knowledge
Runbooks, service maps and policies live in wikis. Getting them into an agent means an ingestion path and a refresh story, separate from memory.
A knowledge base per workspace, searchable alongside memory and kept distinct from it, because they answer different questions. knowledgebase_search
Multiple agents
What one agent learns, the others need. Memory that only serves the agent that wrote it is a cache, and you will build the sharing layer eventually.
Namespacing per agent, cross-agent search within a workspace, and a one-way promotion path from private memory into shared knowledge. agent_id · memory_promote
Isolation and governance
Per-tenant separation, rights on who may publish to shared knowledge, deletion on request. This is usually what blocks going to production.
Workspaces are the isolation boundary. Promotion to shared knowledge requires rights on the workspace rather than trust in the caller. datapack · scoped credentials
Cost and traceability
Retrieval is not free — every search and every write embeds text. You cannot optimise what you cannot attribute, and you cannot vouch for an unattended agent whose decisions you cannot replay.
Usage tracking and conversation-scoped tracing, so retrieval cost lands on the run that caused it and the run can be replayed. track_token_usage · conversation_*
The category

A context engine is not a vector database

One returns text that resembles your query. The other decides what the model should be given — and what it can skip.

A vector store answers

"Which stored chunks look like this query?" It hands back text. Everything after that — whether the match is good enough, whether it is still true, whether to act on it, what it cost — is yours to build.

A context engine answers

"Given this decision, what should the model be given?" It assembles memory, organisational knowledge and policy into a scored, attributed context — and it is allowed to return nothing, which is the answer that makes the rest trustworthy.

The distinction matters most at the moment an agent decides not to do work. A retrieval layer that only ever returns its best guess cannot support that decision, because the best guess is always something. An engine that reports how good the match is, where it came from and whether it is still current can — and that is what lets memory change the plan, not just the answer.

Why this matters more for agents than for chat

Four properties of agents that make context critical

They repeat

A chatbot's conversations are mostly novel. An operational agent sees the same incident class over and over. Without memory, you pay full price for a question you have already answered — and the repetition is exactly where the margin is.

They act

Acting on a stale fact is worse than returning nothing. Recall alone cannot tell you whether a remembered fix still applies to a system that has moved since. That needs a freshness signal the agent can check before it commits.

They plan

Context that arrives before the agent decides what to do changes what it does. Context that arrives afterwards only dresses up the answer. To shape the work, retrieval has to be cheap enough to run first — a design decision, not something you tune later.

They multiply

One becomes several: a deploy bot, a triage agent, an on-call assistant. What one learns, the others need, under different identities and different rights. Retrofitting that sharing once three agents are in production is the expensive way to do it.

What you are about to see

The same incident, three ways

Memory changes the plan, and the plan changes the bill. The demo exists to let you check that rather than take it on trust.

Run one

A strong match, and the system has not moved since the fix was recorded. The agent answers from memory without calling the model at all.

Run two

Memory has nothing

An incident memory has never seen. It finds no match and does the full investigation. This is the baseline.

Run three · watch this one

It looks familiar. The system moved.

Same symptom, same strong match — but the service has shipped since, and the stored fix assumed the old version. It declines the old fix and investigates from scratch.

Run three is the one that matters. Memory on its own is just a cache: fast, but blind to change. Memory recalls what happened before; knowledge — runbooks, service maps, policies — says how the system is meant to work. Together they give the agent the right context to make the right call: reuse the fix when it still holds, investigate when it does not. Every run shows its cost in dollars, including what the skipped work would have cost.
